# help.stemcounts

StemCounts help site. A static site built with
[Astro Starlight](https://starlight.astro.build/): Markdown and MDX
content, no JavaScript shipped to the reader by default, served at
`help.stemcounts.com`.

This is **separate from the StemCounts app**, which lives in the
`stemcounts` repo (`mira-advisory/stemcounts`). The help site calls no
StemCounts API and needs no sign-in. Everything a customer reads here is
public.

## How the content works

Three kinds of page, kept current in three different ways.

| Section | Folder | Written by | Kept current by |
|---|---|---|---|
| Getting started, For florists, For wholesalers, Account and billing | `getting-started/`, `florists/`, `wholesalers/`, `billing/` | Hand-written prose, one `.mdx` per article | A person, when the app changes. The app repo's CI (`check-help-links.mjs`) proves every article a support card links to still exists |
| FAQs | `faqs/` | **Generated.** `scripts/import-support-cards.mjs` | Every build, from the app's published support cards |
| Release notes | `changelog/` | **Generated.** `scripts/import-changelog.mjs` | Every build, from the app's published changelog |

**Do not edit a generated page by hand.** Each one starts with a
`GENERATED by scripts/...; do not edit by hand` comment, and the next
build overwrites it. To change an FAQ answer, change the card in the app
repo (`stemcounts/support-kb/topics/*.md`); to change a release note,
change `stemcounts/CHANGELOG.md`. Both are CI-checked there.

### FAQs: the support cards

The StemCounts app answers its Ask StemCounts chat from a set of support
cards, one question and one answer each, checked by the app repo's CI
for format and accuracy. The app publishes the public ones at
`https://app.stemcounts.com/help-cards.json`, and this site turns them
into the FAQ pages, one page per topic, each card a heading with its
answer, a **Where:** line and a **Read more** link to the article it
belongs to.

`scripts/import-support-cards.mjs` reads the cards from the first of
these that works: `--from <path or URL>`, the `HELP_CARDS_URL`
environment variable, the production URL above, then a sibling checkout
at `../stemcounts/backend/api/shared/support-kb.generated.json` (for a
laptop; Amplify has no sibling checkout). It then decides what is
public:

- cards marked for StemCounts staff are never written;
- cards for a feature behind a feature flag are written only when the
  flag is in `RELEASED_FLAGS` inside the script. When a feature is
  released on production, add its key there; that is the one line to
  change.

Answers are written verbatim. The only edits are escaping for MDX and
turning bare URLs into links. The script is deterministic and only
rewrites a file whose content changed, and it removes a generated page
whose topic no longer has any public cards.

### Release notes: the changelog

`scripts/import-changelog.mjs` reads
`https://app.stemcounts.com/changelog.json` (or `--from`, or
`HELP_CHANGELOG_URL`, or a sibling `../stemcounts/CHANGELOG.md`) and
writes `changelog/index.mdx` with the same rules as the app's own What's
new page: one section per release, the headline of each public bullet
only, tagged New, Improved or Fixed. Team-only bullets never reach the
page, whichever source was read.

### When the pages refresh

`npm run build` runs `prebuild` first, which runs both scripts. When the
app's URLs answer, the pages are regenerated from them; when they do not
(no network, or the file is not published yet), the build prints
`... import skipped, using committed pages` and uses the pages committed
in this repo. So the committed pages are always a usable fallback, and
every successful Amplify build describes the app as it is on production
at that moment. To refresh the committed pages from a laptop, run the two
scripts and commit the result.

The URLs are production's on purpose. Customers on production read this
site, and a card or a release note that describes a feature only dev has
would be wrong for them.


The sidebar is generated from the folders (see `sidebar` in
`astro.config.mjs`). A new `.mdx` file in the right folder appears
without any other change.

## Local development

```bash
npm install
npm run dev
```

The dev server runs at <http://localhost:4321> and reloads on save.
`npm run dev` does not run the import scripts; run them yourself to
refresh the generated pages:

```bash
node scripts/import-support-cards.mjs
node scripts/import-changelog.mjs
```

## Build and preview

```bash
npm run build       # prebuild (the two imports), then the static site into ./dist/
npm run preview     # serves ./dist/ locally
```

## Brand tokens

**Everything brand-related lives in `src/styles/custom.css`.** That file
is the single source of truth for this site; the comment block at the
top maps each token back to its source in the app. If a brand colour
changes, change it in both repos in the same commit.

| Token | Value | Use |
|---|---|---|
| `--sl-color-accent` | `#1B4332` (forest green) | Logo accent, inline links, hover borders |
| `--cta-primary` | `#FF6F61` (coral) | Primary calls to action, active sidebar item, hero button |
| Secondary teal | `#2A9D8F` | Logo accent (favicon and brand mark) |
| `--sl-font` | Inter | Body and headings |
| `--sl-radius` | `8px` | Cards, buttons, asides |

Logo source: `src/assets/stemcounts-logo.svg`.

No inline hex literals in components or articles. Always reference the
CSS variables or the `--cta-*` tokens.

## Writing an article

Articles are the hand-written sections only: `getting-started/`,
`florists/`, `wholesalers/`, `billing/`. An article is the concept, one
or two pictures, and a pointer to the FAQ answers; the how-to detail
lives in the support cards, so an article should not describe a button
in its own words when a card already does (two answers drift apart).

1. Pick the section folder under `src/content/docs/`.
2. Add a `.mdx` file. The file name becomes the URL slug.
3. Frontmatter at the top:

   ```mdx
   ---
   title: My new article
   description: One-line summary used for OG tags and the sidebar tooltip.
   sidebar:
     order: 2          # optional, position within the section
   ---
   ```

4. Use Starlight's [built-in components](https://starlight.astro.build/components/):
   `<Steps>`, `<Aside>`, `<Card>`, `<Tabs>`, `<Badge>`. Imported per page:

   ```mdx
   import { Steps, Aside } from "@astrojs/starlight/components";
   ```

5. For screenshots and video, use `<HelpMedia>`:

   ```mdx
   import HelpMedia from "../../../components/HelpMedia.astro";

   <HelpMedia id="catalog-browse" />
   ```

   See [`src/components/HelpMedia.astro`](src/components/HelpMedia.astro)
   for the props (alt, caption, kind, width, figure).

6. Never an em or en dash, anywhere on the site. A comma, a colon, a full
   stop or brackets instead. A plain hyphen is fine where a hyphen is
   meant.

7. Never a page or a line about tools only StemCounts staff can see.
   This site is public.

## Images and video: the help-media bucket

Each `<HelpMedia id="slug" />` resolves straight to a file in S3:

```
https://help-media.stemcounts.com/{slug}.{ext}
```

`ext` is `png` for images (the default) and `mp4` for video
(`kind="video"`). The bucket is flat, no folders, and there is no
manifest: a file with the right name appears on the next page load. If
the file is not there, `<HelpMedia>` shows a visible "Missing media"
card with the exact filename and a copy button, so a missing picture is
easy to spot on the live site and never breaks the build.

**Where the pictures come from.** They are shot from the real app, not
drawn or pasted by hand. `scripts/help-shots/` in the app repo
(`shoot.cjs` and one script per section) drives the app on dev1 with
Playwright, hides the dev-only chrome, blurs phone numbers and street
addresses, and saves every slug this site expects at the checklist's
size into one handover folder with the exact filenames. Uploading that
folder to the bucket is the remaining manual step. The shoot reads the
slug list from this repo's `docs/HELP_MEDIA_CHECKLIST.md`.

**Keeping the checklist true.** `docs/HELP_MEDIA_CHECKLIST.md` is
generated from the `<HelpMedia>` calls in the articles. After adding or
renaming one, regenerate it:

```bash
python scripts/list-help-media.py
```

## Deploy

The site is live at `https://help.stemcounts.com`, served through
CloudFront. The build spec is [`amplify.yml`](./amplify.yml): `npm ci`,
then `npm run build` (which runs `prebuild`, the two imports, first);
artifacts are `dist/`. No server side rendering and no Lambda, a static
site on a CDN. Cache headers are in [`customHttp.yml`](./customHttp.yml):
HTML revalidates every 5 minutes so a deploy reaches readers quickly.

A build regenerates the FAQ and Release notes pages from the app's
published files, so the site keeps up with the app when it is rebuilt.
Rebuilds happen on a push to `main`; a rebuild without a push (when the
app's cards or changelog change) needs a trigger on the hosting side,
which is a decision for whoever runs the AWS account.

## SEO

- `@astrojs/sitemap` writes `/sitemap-index.xml` at build time.
- [`public/robots.txt`](public/robots.txt) points crawlers at the sitemap.
- `site` in `astro.config.mjs` controls canonical URLs and OG tags and
  must match the live host exactly.
